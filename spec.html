Complete implementation-grade specification. Six modules, one contract: hexagonal @yurifrl/hub core, hub CLI, Hub Console web, omp plugin, and the agent that makes every surface open on what needs attention.

pi-hub — Architecture

Scope: the hexagonal core (@yurifrl/hub), the host packages (@yurifrl/hub-cli, @yurifrl/hub-web, the omp plugin @yurifrl/pi-hub), their boundaries and import rules, the core abstractions, the error model, testing strategy, and repo conventions. Schemas of ~/.hub/ files and hub.sock frames are owned by docs/02-data-contracts.md; commands, routes, tools, and agents by 03–06.

Architecture

Decision. pi-hub is hexagonal (ports & adapters), package-oriented, and DRY. One word names everything: the platform you install is pi-hub, the core library is @yurifrl/hub, the nerve is hub.sock, the CLI is hub, the web app is the Hub Console, the omp tools are hub_*, the data root is ~/.hub/.

Layers:

layerwhererule
domainlib/domain/pure TypeScript types and pure functions. Imports nothing: no node:, no bun:, no @earendil-works/*, no other layer. Values in, values out.
portslib/ports/interfaces the core needs from the outside (StatusStore, SummaryStore, AttentionStore, EventBus, AgentRuntime, Clock). Imports domain only.
adapterslib/adapters/implementations of ports at the edges: filesystem, JSONL, omp subprocesses, unix socket, SSE. Imports ports + domain. All I/O lives here; zero domain logic — adapters translate between the outside world and the core.
hostsextensions/hub.ts, cli/, web/composition roots: instantiate adapters, inject them into ports, expose surfaces. No domain logic; parsing and presenting only.

Why. The domain must stay testable without pi, without the filesystem, and without sockets — that is the point of the hexagon. Keeping hosts as thin composition roots means a new surface (a TUI, a widget, a second web view) is a renderer plugin over the same CommandSurface, not a fork of business logic. Package-oriented layout (one capability = one package with its own package.json and public index.ts) keeps workspaces independently type-checkable and makes "who may import whom" a checkable fact instead of a convention.

Rules the matrix encodes:

  • lib imports nothing from omp or @earendil-works/*. The extension entry is the only consumer of host types.
  • @earendil-works/pi-coding-agent and @earendil-works/pi-tui are optional peerDependencies of the root package only, so the plugin compiles against whatever the host ships and renders through the host's TUI. lib, cli, and web never reference them.
  • extensions import lib; cli and web import lib only — never each other, never the extension, never omp types directly.
  • Any deep import across a package boundary (@yurifrl/hub/domain/session) is a defect; only barrels and documented adapter subpaths cross.

Why. lib is a workspace so hosts resolve it by name (@yurifrl/hub) instead of relative paths, which makes the import matrix enforceable per package. The peers stay optional on the root because only extensions/hub.ts runs inside omp; hub and the web server must install and run on a machine that has never seen pi.

Module boundaries

1. Dependencies point inward only: adapters → ports → domain. The domain never imports a port; ports never import adapters; no layer imports a host.

2. Hosts reach lib only through the barrel (@yurifrl/hub) or documented adapter subpaths. Deep imports across packages are defects.

3. extensions/hub.ts is composition root only: it registers the reporter (session_start with attached flag, user_message, assistant_message, tool_call, agent_end frames), the 9 hub_* tools, and the widget — nothing else. Domain logic found in the extension is in the wrong package.

4. Single writer: exactly one hub process per data root exists at a time, and it is the only writer of status.json (atomic tmp+rename). cli, web, and the plugin are read-only observers that mutate exclusively through ops over hub.sock (cmd/reply frames correlated by cmdId, version handshake field on connect). Startup races are resolved by an exclusive lock taken at boot (mechanism owned by 02-data-contracts).

5. One capability = one package. There is no utils.ts, helpers.ts, or misc.ts anywhere in the repo; see Conventions.

6. Runtime writes stay inside ~/.hub/. No package writes outside pi-hub/ at build or dev time without explicit approval; the extension never edits pi settings or syncs files into ~/.pi/.

7. Agent surfaces are data, not code: an agent declares an agentSurface id, and each host registers a renderer per id (default watcher, demo pending); per-agent state lives in ~/.hub/agents/<name>/surface.json. A host that has no renderer for a declared id renders the raw stream only — it never guesses.

Core abstractions

All types below are defined once in lib/domain/. Fences are type sketches only — no runnable code.

// lib/domain/command.ts — shared vocabulary for every port result and surface reply
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

type HubCode = "unavailable-hub" | "unknown-session" | "timeout" | "denied";

type HubError = {
  code: HubCode;
  message: string;        // human text, presentable as-is by any surface
  retryable: boolean;     // true only for transient unavailable-hub / timeout
  cause?: unknown;        // structured detail, never a thrown Error instance
};

// lib/domain/command.ts — the one op registry every surface speaks
type OpName =
  | "list" | "attention" | "answer" | "assign" | "send"
  | "tool" | "spawn" | "kill" | "archive" | "logTail" | "summaries";

type Caller = "cli" | "web" | "plugin" | "agent";

type CommandRequest = {
  cmdId: string;                     // correlation id echoed by reply frames on hub.sock
  op: OpName;
  args: Record<string, unknown>;
  by: Caller;
};

type CommandReply = Result<unknown, HubError>;

type CommandSurface = {
  dispatch(req: CommandRequest): Promise<CommandReply>;
  ops(): OpName[];                   // registry inspection feeding --help and tool schemas
};

The op set is the whole action vocabulary of the platform. The nine omp tools map onto it (hub_list_sessions → list, hub_send_message → send, hub_call_tool → tool, hub_spawn_worker → spawn, hub_kill_worker → kill, hub_archive → archive, hub_attention → attention, hub_answer → answer, hub_assign → assign); logTail and summaries are cli/web-only reads with no omp tool. Schemas per tool are owned by 05-omp-plugin.

  summaries: SummaryLine[];                  // tail, already filtered

  | { kind: "orientation"; text: string }            // the agent-written one-liner
  | { kind: "attention"; items: AttentionItem[] }
  | { kind: "running"; sessions: SessionRecord[] }
  | { kind: "idle"; sessions: SessionRecord[] }

Renderers are pure snapshot→view-model functions; the medium (ANSI, HTML) is applied by the host's paint layer using lib/theme.ts tokens. This is what makes terminal, web, and widget render the same hierarchy — orientation, needs-you, running, idle, stream — from one implementation.

Error model

Decision. Errors are values, not exceptions. Every port method returns Result<T, HubError>; nothing throws across a port boundary. Adapters may throw only for programmer errors — assertion failures, misconfiguration at construction — never for expected runtime conditions. This is what lets a reply frame on hub.sock carry any failure losslessly and lets every surface render every failure.

Taxonomy — a closed set of four codes:

Contract. The code set is closed; the exact cli table is owned by 03-cli, the HTTP mapping by 04-web — this doc fixes the codes and the rule that they are data. Forward compatibility: a surface receiving an unknown code (newer hub) renders a generic failure with the message text instead of crashing. retryable: true marks the only cases where a surface may auto-retry (unavailable-hub reconnect, timeout re-ask with a fresh cmdId); everything else is terminal for that request.

Testing

Decision. bun test per package, zero shared test configuration; test files are *.test.ts colocated next to the module they exercise. Adapters receive dataRoot and socket path as constructor arguments — tests never touch the real ~/.hub/ and never need a new env var for isolation.

  • Domain pure unit: every domain function is deterministic given an injected Clock; there is nothing to mock because there is nothing to inject but data.
  • Adapters vs temp dirs: each adapter test builds its own temp dataRoot, so tests run in parallel without cross-talk and a crashed test leaves no residue.
  • One e2e: a single test assembles the real composition root — hub process with a temp data root and a unix socket at a temp path — plus two fake sessions (scripted fixtures that emit reporter frames and answer cmd frames). It asserts the full spine: session_start lands both sessions in status.json; a tool_call proposing approval raises an AttentionItem; the answer op resolves it and appends a kind:"resolution" line to summaries.jsonl; archive moves the closed record to archive/YYYY-MM/<id>.json. This is the only test that spans packages; everything below it is unit or integration.

Conventions

  • File naming: kebab-case modules (json_store.ts, status_store.ts), PascalCase exported types, one module = one cohesive concern. Test files are *.test.ts colocated beside the tested module; larger fixtures live in testdata/ under the owning package.
  • Barrel exports: each package exports only through its index.ts (@yurifrl/hub), plus adapter subpaths declared in lib/package.json exports. Reaching past a barrel from another package is a defect.
  • No default exports except bins: cli/src/bin.ts (bun bin entry) and extensions/hub.ts (omp loads it as the plugin entry) are the only default exports; everything else is a named export so tree-shaking and grep stay honest.
  • No grab-bag utils: utils.ts, helpers.ts, misc.ts, common.ts are banned. Shared code is either a domain concept (moves into lib/domain) or a recorded deliberate duplication (table above).
  • No side effects at module load: everything runs from entry handlers or main(); adapters do work only when their methods are called.
  • Function shape: max ~2 nesting levels — extract a function instead. No giant handlers: a host handler parses, dispatches one CommandRequest, and forwards the reply to the paint layer.
  • Docs are decision records: each doc states decision, why, contract; H1 + one-line scope sentence, H2 sections, dense markdown, types in fences, no emoji, no runnable code.

pi-hub — Data contracts

On-disk and wire contracts for the hub — status.json, logs/<id>.jsonl,

summaries.jsonl, the archive/YYYY-MM/ tree, and the hub.sock frame

protocol; this doc is the shape and frame owner, and 03, 04, 05, 06 are

consumers that reference it, never restate it. Conventions: timestamps are

ISO 8601 UTC strings (e.g. 2026-08-30T17:57:51.401Z); sessionId is the

omp session id verbatim, never re-encoded or shortened; attention item ids

are hub-minted att-<n> from the monotonic counter nextAttentionId in the

meta block, so ids survive hub restarts; all types live once in

lib/domain/ (01-architecture), tables here are normative field lists, and

fenced ts blocks are type sketches only — no imports, no runtime code.

status.json

~/.hub/status.json is one JSON object holding every live fact: the hub

meta block, the sessions map, open attention[] items, and the

archived[] tombstone index. It is the only mutable state file; everything

else is append-only logs or immutable archive records.

Single writer: only the hub process writes it. Enforcement is an

exclusive flock on ~/.hub/hub.lock held for the hub's lifetime; a

second hub instance fails to acquire the lock and exits (CLI exit code 2 —

unavailable). CLI and web never write the file — they read it directly or

take a list reply over hub.sock; every mutation flows through an op

that only the hub process applies.

Atomic rewrite: writers replace the whole object — serialize, write

status.json.tmp, fsync, rename(2) over the target. Readers observe

either the previous or the next complete object, never a torn file. A

stale status.json.tmp is unlinked by the hub on start.

Capped at 200 entries; on overflow the oldest link is dropped. The archive

tree itself is never pruned — archived[] is a recent-closers index for

boards, not the history of record.

Invariants

1. Open until closed. A session exists in sessions from

session_start until a proper close: the kill op, a reporter

farewell (agent_end with reason:"exit"), or the hub-restart reaper

(invariant 8). A crashed reporter does not close its session — the

record stays until a close path runs.

2. Close path is remove-then-archive, one rename. On close the record

is deleted from sessions, the full record is written to

archive/YYYY-MM/<id>.json (with closedAt, closedBy,

finalSummary, resolution tail — ## archive), and an archived[]

link is appended. All three land in a single atomic status.json

rewrite, ordered after the archive file is durably written.

3. log is a link, never content. Status must stay small and cheap

to rewrite on every event; the raw stream lives in logs/<id>.jsonl.

4. Single writer. Exactly one hub process (flock-guarded) writes;

every other process reads.

5. Atomic rewrite for every write (tmp + fsync + rename).

6. Unknown fields ignored. Readers tolerate unknown fields at every

level — forward compatibility (## Versioning).

7. version is the first field of the meta block, so a reader can

reject an unknown future format before parsing further.

8. Crash recovery. On start the hub loads the existing status.json;

sessions that do not re-announce via session_start within a 60s

grace window are closed and archived with closedBy:"hub-restart" and

a finalSummary synthesized from the record's last description.

Reporters announce on every start, so a still-running omp session

re-attaches and keeps its record untouched.

hub.sock

$OMP_HUB_SOCK (default ~/.hub/hub.sock) — a Unix domain SOCK_STREAM

socket. The protocol is newline-delimited JSON frames in both directions:

one JSON object per \n-terminated frame, UTF-8, no framing escapes.

Every frame carries v (frame-protocol version, currently 1). The hub

is the server; clients are the plugin reporter (one connection per

session), the CLI (one-shot cmd/reply), the web server (long-lived,

subscribed), and the hub agent (long-lived, subscribed).

Handshake

First frame from any client:

{ "v": 1, "ch": "hello", "client": "cli", "subscribe": false }

client is cli | web | plugin | agent; subscribe: true (web server,

hub agent) additionally opts into unsolicited event frames (below). The

hub replies { "v": 1, "ch": "hello", "hub": { "version": 1, "startedAt": "..." } }.

A major-version mismatch is answered with an error frame (bad-version)

and the connection is closed; minor drift is tolerated — unknown fields

ignored, the same rule as status.json.

Reporter frames (plugin → hub, `ch:"report"`)

Emitted by the omp plugin (05-omp-plugin) as the session runs. Shape:

{ v, ch:"report", frame: <name>, ...payload }. Reporter frames are

fire-and-forget — no reply, no cmdId; socket order is record order.

authoritative snapshot.

Error frames and concurrency

Protocol-level failures (bad v, malformed JSON, unknown ch) get an

unsolicited { v, ch:"error", error: { code, message } } frame with

cmdId when one is known; malformed input closes the connection. Error

codes: bad-frame, bad-version, unknown-op, forbidden,

no-session, timeout, busy. The hub serializes all state mutations

(single-writer); concurrent cmds interleave and correlate by cmdId. A

kill of a session with in-flight cmds fails those cmds with

no-session.

Attention lifecycle

Attention is the queue of things a human should look at. It is

agent-mediated: the hub agent (06-agents-and-skills) watches all

threads and raises items; surfaces render them; humans resolve them.

attention[] in status.json holds open items only — resolution removes

the item and appends the permanent record to summaries.jsonl.

action:"raise"; the hub verifies the caller — hello client:"agent"

the older item resolved.

is their only history, and the session's archive record folds them into

its resolutions tail.

Assign. The assign op (hub_assign, web assign input, board a

target session: AttentionItem { kind:"idle", text: "assigned: <task>" }.

It stays open — the visible marker of outstanding work — until the hub

agent sees the session leave idle (auto-resolve) or a human dismisses

or answers it. With the agent off, assigned items resolve only manually.

Rendering tie-in. This section is data-only; color belongs to

lib/theme.ts — open items render in the attention color (warn

selection chrome in accent #70e1c4. The widget (05) and the CLI board

Versioning

  • status.json carries version (currently 1) as the first meta

field. One integer, additive meaning: a bump signals "readers written

for the previous version must still work" — it is required only when a

field's meaning changes, never when fields are added.

  • Forward compatibility: readers ignore unknown fields at every level

(meta block, SessionRecord, AttentionItem, socket frames, log and

summary lines). Writers never remove or repurpose fields within a

version. The phase and kind enumerations may grow; readers treat

unknown enum values as opaque strings (render generically), never as

errors.

  • Wire: hub.sock frames carry v; the hello handshake

negotiates. A major mismatch gets bad-version and a close; because

the framing is NDJSON with a version per frame, a hub upgrade can serve

mixed client versions across a rolling restart.

  • Append-only files: logs/<id>.jsonl and summaries.jsonl have no

header or version line — their contract is "additive fields only; files

are never rewritten". If a breaking change is ever unavoidable, the

file rotates (summaries-2.jsonl) and the active generation is named

by a new optional meta field summariesGeneration (decision: rotation

over in-place rewrite; rewriting append-only files would break every

concurrent reader).

  • Archive records embed the version they were written at (optional

field), so old records stay interpretable if the SessionRecord shape

ever drifts.

  • Atomicity, restated: every status.json rewrite is tmp-write →

fsync → rename. Rename is atomic on POSIX; readers never lock. A crash

between write and rename leaves status.json.tmp, which the next hub

start unlinks. The flock on ~/.hub/hub.lock guarantees one writer

across crashes — a dead hub's lock dies with it, so a restart can

always take over and run crash recovery (invariant 8).

Bare hub opens the attention board: the terminal rendering of status.json's attention[] and sessions map, kept live. It answers one question on open — what needs me? — and lets you act without leaving the screen.

4. 💤 IDLE — one row per session in phase idle: ▎○ <name> idle <age> assign: _. Each row owns an inline assign input; typing + ⏎ issues cmd frame assign {id, task} and the session flips to working.

5. Footer — one muted keys-hint line.

  • Human: ✓ answered <item> → <name> in ok, the delivered text echoed muted.
  • --json: {type:"snapshot", data:{answered:true, id, sessionId}}; --ndjson: same, one line.
  • Errors: unknown/ambiguous item → 1; hub unreachable → 2; reply timeout → 3.

  • Human: ✓ assigned to <name> — <first line of task>.
  • --json: {type:"snapshot", data:{assigned:true, id, sessionId, task}}.
  • Errors: as answer; picker over zero candidates → not_found 1.

Rendering

All rendering lives in cli/src/render/; commands never emit ANSI themselves — commands produce data, renderers produce frames.

Theme → ANSI. lib/theme.ts is the single token definition (ownership in 01-architecture.md); the CLI maps each token to escape sequences:

Session hue. session-hue = hash(sessionId) mod 216, rendered as cube index 16 + h — the 6×6×6 cube, skipping the 16 base terminal colors. Every line belonging to a session is prefixed with a two-cell bar ▎ in that hue: board rows, log lines, picker rows. Decision: the hue derives only from sessionId, never from the name. Why: names change (worker-3 renamed), ids do not; the bar must keep tracking the session across every surface. Contract: 04-web.md uses the identical hash so CLI and web agree on a session's color.

Alt-screen lifecycle. The board, watch, the full log view (via o), and pickers enter alt-screen (smcup), hide the cursor while a frame is stable, and restore the terminal on every exit path — q, ctrl-c, error, crash (an exit hook re-issues rmcup and shows the cursor). log -f in a TTY does not use alt-screen: it prints scrolling lines with tail semantics; ctrl-c exits 0.

Re-render triggers. EventBus push frames over the socket, every reply frame, the 2s fallback tick, and keypresses. Frames pass through the diffing buffer; a frame with zero diffs writes nothing.

Raw-mode single keypress. Output policies

Envelope. All machine output is exactly one of:

type OutputEnvelope =
  | { type: "snapshot"; data: unknown }
  | { type: "error"; error: { code: ErrorCode; message: string; detail?: unknown } }

type ErrorCode =
  | "usage"        // exit 1 — bad args, parse failures
  | "not_found"    // exit 1 — unknown id/item
  | "ambiguous"    // exit 1 — prefix matched several
  | "busy"         // exit 1 — e.g. agent already running
  | "unavailable"  // exit 2 — socket missing/refused, port busy, omp binary missing
  | "protocol"     // exit 2 — version mismatch, malformed reply
  | "timeout"      // exit 3

  • Decision: interactive surfaces under machine modes degrade to static snapshots rather than erroring. Hub Console

The Hub Console is the @yurifrl/hub-web surface: a zero-framework Bun server that renders ~/.hub/ state as server-side HTML strings and keeps it live over SSE (GET /stream). It is an action-oriented renderer, not a log viewer — like the CLI board and the omp widget, it opens on what needs you and demotes the raw stream to a secondary panel. It reads status.json and summaries.jsonl through the same StatusStore / SummaryStore / AttentionStore ports the CLI uses, writes only through the hub's command surface (answer, dismiss, assign, send), and never touches the single-writer file directly: the hub process remains the only writer of status.json. No client-side framework, no build step, no hydration — the server renders HTML strings, the browser applies SSE deltas to a tiny in-memory state object. A page is a renderer plugin over the same shared domain types (AttentionItem, SessionRecord, Summary) every other surface consumes; nothing here parses logs or re-derives attention.

All HTML routes render from the latest in-memory snapshot (warmed from status.json at boot). All API routes are JSON in / JSON out and write through the command surface. GET / is the attention console — the web twin of bare hub — and is the default landing page.

Route rules:

  • Archived flavor is data-driven, not a separate template: /session/:id looks in open sessions first, then the archive; a closed session renders with the closed badge, close date, and final summary pinned (see Session detail).   • Unknown :id on /session/:id → 404 page listing open sessions (so a stale link still lands somewhere useful). Unknown item id on any POST /api/* → 404 {"error": "unknown item"}; malformed JSON body → 400 {"error": ...}.
  • /agent with no live hub agent renders the registry as empty-state ("no hub agent running — start with hub agent"), not an error.
  • POSTing to a closed/archived session (/api/send with an archived sessionId) → 409 {"error": "session closed"}; the CLI surfaces the same refusal.

SSE contract

One endpoint, GET /stream, text/event-stream, one logical channel. Events carry id: fields so the client can reconnect; payloads are JSON. The server emits in hub-phase order — when something changes, the smallest event that describes the change goes out; a snapshot is always sufficient state on its own.

eventpayloadwhen
snapshot{v, digest, attention: AttentionItem[], sessions: SessionDigest[]} — full attention + sessions state, same shape GET /api/status returnson connect (first event), after reconnect, and after any server-side state that cannot be expressed as a delta (agent restart, archive sweep, version bump)
attention`{op: "raised"\"resolved", item: AttentionItem}` — raised/resolved deltas for one itemhub agent raises or an answer/dismiss resolves an item

Reconnect semantics:

  • EventSource reconnects automatically with Last-Event-ID. The server keeps a small ring of recent event ids (per connection it tracks the last emitted id); on reattach with a Last-Event-ID it replays what the ring still holds and then sends a fresh snapshot — the client treats any snapshot as authoritative and replaces state wholesale, so replayed deltas are idempotent (deltas are keyed by item id / session id, so re-applying is safe).
  • Missed-beyond-ring reattach degrades to just the snapshot refresh; that is the designed behavior — the snapshot is the contract, deltas are an optimization.
  • The snapshot payload is the single full-state shape; GET /api/status returns exactly it. One shape, two transports.
  • Web-package extension: /agent pages may also emit a surface delta ({name, json}) when a watched ~/.hub/agents/<name>/surface.json changes (see Agent page). The five events above are the core contract every client must handle; surface is consumed only by custom agent pages.

Main page

GET / renders top-down in this exact order — same hierarchy as the CLI board and omp widget:

1. Orientation line — one agent-written sentence under the header: what needs you first ("tilt needs approval · deploy canary 2/3 · docs idle 12m"). Sourced from the hub-agent digest field in status.json; when the agent is off, the server synthesizes counts ("2 need you · 3 running · 1 idle"). Updated via phase deltas carrying the new digest, or a fresh snapshot.

2. Attention cards (amber-bordered, warn token) — one per AttentionItem, kind-tagged (approval / question / blocked / idle). Each card: kind chip, session hue bar + session id, item text, and three verbs as first-class inline controls — the answer input lives on the card (type + Enter → POST /api/answer, delivers to the session and resolves), dismiss ✕ (→ POST /api/dismiss), open → (link to /session/:id). All four kinds use the same three verbs — answering a kind-idle item nudges its session; assigning idle sessions is the separate idle-assign section below.

3. Running strip — one digest line per active session (working / waiting / blocked): hue bar, phase word, agent-written description. Not the log — a digest. Each line links to /session/:id. A waiting line carries its attention count.

4. Idle-assign cards — one per idle session: hue bar, id, idle-for duration, and an "assign work" input right on the card (Enter → POST /api/assign).

5. Collapsed stream — a chip (▸ stream (n)); toggling expands the full hue-tagged live log (the log events, newest at bottom). Collapsed by default; the stream never disappears, it just stopped being the headline. Toggling sends no request — the client keeps receiving log events and shows/hides the panel.

6. Summary rail — right column, latest summary lines from summaries.jsonl (per-session tinted), newest first, each linking to /session/:id. resolution lines render inline with the answer text.

Keyboard: a focus next attention card input, s toggle stream, / focus filter, Enter submits the focused input, Esc blurs. Filter hides non-matching cards and strip lines (client-side only).

Session detail

GET /session/:id — the full-record view; the raw log lives here, demoted from the main page but first-class quality.

  • Full log via the LINK, not embedded: the session record in status.json carries log: "logs/<id>.jsonl" — a link, never content. The server reads that file through the store adapter per request (bounded tail + ?since= cursor param for live tailing) and renders hue-tagged entries. The web server never inlines log bytes into status.json reads.
  • Phase timeline: horizontal rail of the session's phase history from the record's bounded phaseHistory ({phase, at}[], newest right, cap 50). Absent field → timeline shows the current phase only. blocked and waiting segments render in warn/err, working in ok.
  • Tool bars: one compact row per tool_call log entry — tool name, arg digest, duration, ok/err dot. Collapsed by default per tool kind; click expands the result.
  • Pinned send box: bottom-pinned input, always visible; Enter → POST /api/send {sessionId, text}; delivery state (queued → delivered) shown inline from the response.
  • Archived flavor (closed session): closed badge, closedAt date, closedBy, and the final summary pinned above the log; the send box is replaced by a "closed — read-only" note, answer/assign controls absent. Same renderer, data-driven flavor.

Agent page

GET /agent renders the hub agent's declared custom surface — the agent owns its interface.

  • Surface registry: a static map in the web package from agentSurface id → renderer function. Surfaces register per id; the page looks up the agent record's agentSurface and hands the panel the record's fields. This is the DRY web-side expression of the surfaces contract: one registry, renderers are pure functions from agent state to HTML.
  • Default watcher surface: a compact panel — digest line, attention counts (⚠ n ⏳ n 💤 n), last summary, cadence heartbeat. It mirrors what the CLI hub agent --surface watcher shows, rendered in HTML.
  • Demo pending surface: renders ~/.hub/agents/<name>/surface.json as a self-updating panel. The server watches that file (mtime poll) and pushes a surface-namespaced delta over the same /stream connection when it changes; the client re-renders the panel from the JSON payload. No client polling, no reload.
  • Unknown agentSurface id → generic card: agent name, kind, digest, link to its session detail. Never a 404 — the registry degrades, it does not fail.
  • The hub agent is optional (default off). With no agent, /agent renders the empty-state described under Routes and the main page hides attention/summary rails (fallback stream-only mode).

Server

@yurifrl/hub-web exports one entry, startHubWeb — the composition root injects stores, bus, and command surface; the package holds no file I/O of its own beyond reading the log/surface files through injected ports. Port shape (type sketch, no imports):

type HubWebDeps = {
  port?: number;                 // default 7749 (final default owned by 03-cli), binds 127.0.0.1 only
  stores: {
    status: StatusStore;         // read status.json + sessions map
    summaries: SummaryStore;     // tail summaries.jsonl
    attention: AttentionStore;   // read/answer/dismiss attention items
  };
  bus: EventBus;                 // hub event bus; web subscribes, never publishes state
  commands: CommandSurface;      // answer / dismiss / assign / send — all writes go through here
  logs?: {                     // shape the web package needs; satisfied by injecting
    tail(id, since?): Entry[]; // the lib jsonl_store adapter — reads logs/<id>.jsonl
  };                           // via the status.json log LINK. Not a new lib port.
  theme?: ThemeTokens;           // defaults to lib/theme.ts
};
type startHubWeb = (deps: HubWebDeps) => Promise<{ stop(): Promise<void>; port: number }>;
  • Bind address: 127.0.0.1 default, non-configurable in v1. The console is a window onto your local agents' session content and can answer on your behalf — it must not be reachable from the network by default.
  • Security tradeoff (v1 = local-only, no auth): we deliberately ship no token/session auth. Why: the hub is a single-user, same-machine tool; the socket and the web server already assume a trusted local user, and auth would add a secret-management surface (where does the token live, how does the browser get it) that outweighs the threat for v1. The tradeoff we accept: any local process or user on the machine can read every session's log content and post answers as you. That is exactly the trust boundary hub.sock already assumes (same-user unix socket), so the web surface adds no new exposure — it just makes the same assumption explicit. Mitigation that ships anyway: bind to loopback only, no CORS headers on API routes (browsers block cross-origin POSTs with JSON bodies; no Access-Control-Allow-Origin is emitted), Content-Type: application/json enforced on API responses. Future: token auth (env-provided token, required as query param on /stream and header on API routes) behind an explicit opt-in flag — designed but not built in v1.
  • Rendering: server-side HTML template strings, hand-rolled, one function per page (match-day web style: small named functions, no framework, no client bundle). CSS custom properties are generated from lib/theme.ts tokens (--accent: #70e1c4; --ok: #3fd68f; --warn: #f5c04e; --err: #ff7a9a; --muted: #8b97b0; plus per-session hue variables --hue-<sessionId>); the theme is defined once in lib and injected here — the web package never hardcodes a hex value.
  • Static assets: one small inline <style> and <script> per page (no separate files, no build step); CSP default-src 'none'; style-src 'unsafe-inline'; script-src 'unsafe-inline'; connect-src 'self' — inline is deliberate, the pages are served from one origin and the alternative is a build step.
  • Lifecycle: startHubWeb subscribes to the bus on start, unsubscribes and closes all SSE connections on stop(). hub web [--port N] is the CLI wrapper around it.

Client state

The client is a dumb cache with one invariant: the snapshot is authoritative; deltas are idempotent.

  • On load: fetch /api/status → hold as state → open /stream → apply deltas.
  • snapshot replaces state wholesale. attention deltas upsert/remove by item id (op: "raised" → upsert; op: "resolved" → remove + mark resolved in the summary rail). log appends to that session's stream buffer (bounded ring, oldest dropped). summary prepends to the rail. phase updates the session's phase + description.
  • On reconnect (EventSource fires error then re-opens with Last-Event-ID): server responds with replay + fresh snapshot; the client replaces state on snapshot. Because deltas are keyed by id, a replayed delta after a newer snapshot is a no-op unless it carries a newer t.
  • No client-side derived state beyond the filter query and scroll position; every render is a pure function of state. Rerender on each delta is fine at hub scale (tens of sessions); if the stream panel gets hot, only it re-renders.

omp plugin

extensions/hub.ts in @yurifrl/pi-hub — the omp extension that turns any session into the hub and wires every other session to it, as a thin driving adapter over @yurifrl/hub.

The plugin owns no policy. Persistence, attention, summaries, and routing live in lib behind ports (StatusStore, SummaryStore, AttentionStore, EventBus, AgentRuntime, Clock); the extension only translates pi events into hub frames and hub replies into tool results, and renders the widget. The lib composition root (see 01-architecture) is injected with adapters (json_store, jsonl_store, omp_agent, unix_socket, sse_bus) when the hub starts. Key decisions are recorded as DECISION / WHY / CONTRACT blocks, match-day style.

Entry

One default export; all state lives inside the factory closure:

// extensions/hub.ts — @yurifrl/pi-hub entry
export default function hub(pi: ExtensionAPI): void

DECISION — brain early-return.

WHY: hub-spawned RPC children — the omp --mode rpc brain and workers — load the same extension and get OMP_HUB_BRAIN=1. Without a guard every child would try to serve the socket or report to itself, forking the hub forever. (The hub agent does NOT get this flag; it loads the extension fully and is bounded instead by guards 5–6 in ## Anti-recursion.)

CONTRACT: when process.env.OMP_HUB_BRAIN === "1", the factory returns before any pi.on, pi.registerTool, or pi.registerCommand. The child contributes nothing but RPC answers. This is the first and hardest anti-recursion guard (## Anti-recursion).

Commands, registered only after the guard:

commandbehavior
/hub-startmake this session the hub (steps below)
/hub-stopstop serving; keep the session running (## Shutdown)
/hub-agentspawn or adopt the hub agent (## Agent spawn)

/hub-start, in order:

1. setWidget("omp-hub-stream", ...) — claims the widget slot. The key omp-hub-stream is the contract with omp's UI: stable across renders, cleared on /hub-stop.

2. Compose the core: json_store → StatusStore (~/.hub/status.json), jsonl_store → logs + SummaryStore (summaries.jsonl), sse_bus → EventBus, AttentionStore over the StatusStore. Inject into the lib composition root.

3. Spawn the brain through the AgentRuntime port (omp_agent adapter): OMP_BIN --mode rpc, env OMP_HUB_BRAIN=1, plus OMP_HUB_MODEL when set. Readiness = version handshake on the RPC channel.

4. Serve ~/.hub/hub.sock through the unix_socket adapter: newline-delimited JSON frames; reporter events in, cmd/reply out. A stale socket file from a crashed hub is unlinked before listen.

5. Register self in status.json (session record with meta flag kind:"hub") and render the widget.

DECISION — one well-known socket address.

WHY: reporter, hub CLI, and Hub Console must find the hub without config.

CONTRACT: the path is ~/.hub/hub.sock, overridable by OMP_HUB_SOCK; every surface resolves it the same way. The omp-era ~/.omp/hub.sock is dead.

Reporter

Runs in EVERY session — including the hub session, via a local self-feed instead of the socket. One reporter instance per process; every handler follows the error rules (## Tools › Error rules).

Event translation table:

DECISION — two capture paths for user input.

WHY: typed input fires input; messages delivered by the hub or queued by the harness arrive only as user-role message_end. Capturing both is the difference between a roster and a log.

CONTRACT: input is authoritative when present; message_end user-role frames are the fallback and skip <...>-wrapped system payloads so skill injections never pollute the log.

Self-feed: when hubActive && sessionId === selfSessionId, frames bypass the socket and go straight into the hub's event handler. The hub watches itself exactly like a peer, minus the round-trip (and minus recursion risk — ## Anti-recursion).

Attach-on-connect. The reporter owns one reconnecting socket with a bounded outbox (last 500 frames, dropped wholesale above 50 on close). On EVERY successful connect it first enqueues:

{"kind":"session_start","v":1,"attached":true,"sessionId":"a3f2","title":"tilt","cwd":"~/work/api"}

DECISION — attach is a frame, not a handshake endpoint.

WHY: sessions outlive hubs. A session started before the hub — or surviving a hub restart — must appear on the roster with no user action.

CONTRACT: attached:true means "pickup of an existing session"; the hub upserts by sessionId, so reconnects and hub restarts are idempotent — no duplicate rows, no duplicate attention. attached:false appears only in the original session_start emission. All frames carry v:1; a hub that cannot honor the major version replies once with ok:false ("version mismatch") instead of silently dropping frames.

Inbound frames handled by the reporter, exactly two:

  • deliver → sendUserMessage(text) — the only inbound mutation of the host session.
  • reply → resolves the matching pending cmd by cmdId.

Outbound cmds (reporterCmd(op, payload, timeoutMs)): stamp cmdId, enqueue {kind:"cmd", cmdId, op, ...payload}, resolve on reply {cmdId, ok, text}. On timeout: resolve {ok:false, text:"hub command timed out — is the hub running /hub-start?"}. Never throws.

Error rules

  • Every deliver / sendUserMessage call is wrapped in try/catch. A dead target or a hub fault is surfaced in the tool result ({ok:false, text}) — it NEVER throws into the host session. A reporting session must survive hub death, and the hub session must survive a dead peer.

  • Inbound frames are parsed defensively: malformed JSON and unknown kinds are dropped silently.
  • The reporter never writes hub files. Single-writer rule: only the hub process touches status.json, logs, and summaries.jsonl; CLI, web, and reporters read.

Agent spawn

/hub-agent (and hub agent, and the Console toggle) spawn the hub's own agent through the same path as any worker:

  • Child process: OMP_BIN --mode acp, spawned via the AgentRuntime port (omp_agent adapter), env OMP_HUB_AGENT=1 (+ OMP_HUB_MODEL when set). The child is a peer session: it loads the extension normally, reports over hub.sock, and calls the nine tools as peer relay — minimal special casing only (## Anti-recursion guards 5–6: it may not become the hub, and its frames never raise attention).
  • Registration: status.json record with kind:"agent" and agentSurface:"watcher" (declared surface id; surfaces register a renderer per id; default watcher, demo pending). Per-agent surface state lives at ~/.hub/agents/<name>/surface.json.

The watcher's contract with lib — it is the thing that makes the main view:

  • Consume the EventBus and maintain per-session phase (working|waiting|idle|blocked) + one-line description in status.json — the digest lines every surface renders.
  • Append per-turn summaries to summaries.jsonl via SummaryStore ({t, sessionId, kind:"summary"|"resolution", text, by}).
  • Raise and resolve AttentionItem rows via AttentionStore — kinds approval|question|blocked|idle; items resolve with answer + by when hub_answer fires, or get dismissed (resolved without reply) from a surface's answer flow — the resolution lands as a kind:"resolution" line in summaries.jsonl either way.

DECISION — the agent is optional, default off.

WHY: the tool must be useful with zero ceremony; /hub-start alone gives roster + log + relay.

CONTRACT: without the agent, surfaces hide the attention/summary rails and fall back to stream-only mode; the reporter still records everything. At most one hub agent at a time; /hub-agent adopts the existing one if alive.

Shutdown

Hub session_shutdown teardown, in order:

1. Widget cleared (setWidget("omp-hub-stream", undefined)).

2. hub.sock server closed — connected reporters see EOF and enter reconnect backoff.

3. Workers and brain disposed (AgentRuntime.dispose: SIGTERM, then kill after grace).

4. Final StatusStore write (hub meta block updated; peer sessions left as-is).

5. Open attention items are left open — they live in status.json, not in the process.

DECISION — hub shutdown does NOT archive open sessions.

WHY: sessions outlive the hub; archiving them would fake-close live work. On the next /hub-start every reporter reconnects and announces session_start attached:true, and pickup is idempotent (## Reporter).

CONTRACT: archive/YYYY-MM/<id>.json records exist only for proper closes: hub_kill_worker, hub_archive, or a peer's own session_shutdown (which sends session_end; hub closes that one session with closedBy:"session_exit"). Peer rows orphaned by a lost session_end frame are never silently hidden — they carry lastActivity, so staleness is visible in every surface.

Reporter side: on its own session_shutdown the reporter makes one best-effort session_end send and stops; if the hub is already gone the frame is dropped with the outbox and the hub archives the session on cleanup or the row simply stays stale-visible. Nothing crashes: teardown is the same try/catch discipline as everything else.

Anti-recursion

Layered guards, cheapest first. Each is a decision with one job: the hub must never consume itself.

1. Brain guard. OMP_HUB_BRAIN=1 → factory early-return before any registration (## Entry). WHY: children are driven; a child that reports or serves forks the hub forever. CONTRACT: zero pi.on / registerTool / registerCommand in children.

2. Self-feed. Hub-session events enter the local handler directly, never the socket (## Reporter). WHY: the hub consuming its own socket traffic would double-count itself and re-deliver its own output as input. CONTRACT: hubActive && sessionId === selfSessionId → handleEvent, never sendFrame.

3. No self-delivery. A deliver targeting selfSessionId is rejected at the hub (ok:false, "cannot deliver to the hub itself"). The hub agent answers through the AttentionStore, never by messaging the hub session.

4. Attach idempotency. session_start with attached:true for a known sessionId upserts in place; duplicate frames, reconnect storms, and hub restarts never duplicate roster rows or attention items.

5. Agent sessions cannot become hubs. /hub-start in a session with OMP_HUB_AGENT=1 is refused ("this session is the hub agent"). WHY: a hub inside the hub's own agent would recurse the watcher through itself.

6. kind:"agent" isolation. Frames from OMP_HUB_AGENT=1 sessions are recorded in logs but never trigger attention raising or summarization; the AttentionStore rejects items whose sessionId is the agent's. The watcher must not watch itself.

7. One-hop relay, bounded waits. The hub never re-relays a reply as a deliver; cmd → reply is one hop. Every wait is bounded by a per-op timeout, and the reporter outbox is capped, so a dead hub cannot grow memory inside a reporting session.

3. Submit phase + description to the hub writer — the single writer of

status.json. The agent never writes the file itself; it only submits

updates over the control channel.

4. Write summaries (≤2 sentences per session turn) to summaries.jsonl.

5. Raise/resolve attention[] per the detection rules below.

Detection rules — event in, kind and phase out:

tool result waiting on the user (approval prompt, permission request, confirm)approvalwaiting

tool failure the session cannot recover from aloneblockedblocked

Raise rules: one open item per (session, cause); a re-raise updates the text,

never duplicates; resolution happens when the watcher observes the user reply,

the tool proceeding, or the failure cleared — or when anyone answers via

hub_answer, hub answer, or the web console (see Interaction flows).

On restart (crash, reboot) the watcher runs one catch-up pass: it re-derives

phases from status.json and recent summaries, re-raises missing items from

current process state (hub_list_sessions), and resumes the loop. EventBus

events observed during downtime are not replayed; the catch-up pass replaces

replay.

the classification rubric sourced from skills/hub-watcher:

You are the hub-watcher — the hub's own agent. You keep ~/.hub/status.json
truthful and the attention queue actionable. You never do product work.

On every event batch:
1. Attribute each event to its session.
2. Classify the session phase: working | waiting | idle | blocked.
3. Submit phase + description (<= 12 words) to the hub writer.
4. Detect attention. Raise sparingly: an item costs the user a context switch.
   - tool result waiting on the user          -> kind approval
   - assistant output shaped as a question    -> kind question
   - unrecoverable tool failure               -> kind blocked
   - idle past timeout, nothing queued        -> kind idle

Rules:
- One open item per (session, cause). Re-raise updates text, never duplicates.
- Never edit product code, never run repo commands. Your writes are hub ops.
- Unsure? Leave phase "working", raise nothing. A false alarm is worse than
  a late item.

Supervision. A CLI foreground spawn dies with its terminal. Supervised

spawns (web toggle, plugin) restart on-failure with bounded backoff. While

the watcher is down, surfaces keep rendering the last known status.json

(durable state) marked stale; the plugin keeps recording events either way.

agentSurface

Decision. An agent can own its UI: it declares an agentSurface id, and

hub surfaces render that surface from a state file the agent rewrites —

custom surfaces are file-backed; the bundled watcher surface is the one

synthesized exception (from status.json).

Why. Agents know what they want to show — a pending queue, review diffs,

a plan tree. Hard-coding each one into CLI and web duplicates the agent in two

renderers. The file is the interface: renderer plugins read it, the agent

writes it, nobody parses agent prose.

Contract.

1. An agent file declares surface: <id> in frontmatter. The hub exposes the

id on the agent's session record in status.json and via

hub_list_sessions.

2. Hosts register a renderer per id. Bundled renderers: watcher (default —

the attention-board digest) and pending (demo). Registration is

additive; a host lacking a renderer for an id renders the generic card.

3. The agent rewrites ~/.hub/agents/<name>/surface.json — its name, its

file, its writer. This is the deliberate per-file exception to the

hub-only writer of status.json: one writer per file, and here it is the

agent. Rewrite is atomic tmp+rename; revision is monotonic; the file is

capped at 64 KB (renderers truncate sections, never fail); unknown fields

are ignored (forward compat).

4. Unknown id, missing file, or parse failure → generic card: headline plus

sections listed raw. A custom surface can never break a renderer it does

not know.

Type sketches (pure domain types; placement owned by 01-architecture —

SurfaceState in lib/domain/session.ts, the registry as a port beside

CommandSurface in lib/ports):

type SurfaceSection = {
  title: string;
  lines: string[];                 // pre-wrapped, rendered verbatim
  tone?: "info" | "warn" | "err";  // maps to theme tokens; default info
};

type SurfaceState = {
  agent: string;        // agent name; must match the owning ~/.hub/agents/<name>/
  surface: string;      // declared agentSurface id ("watcher", "pending", ...)
  revision: number;     // bumped on every rewrite; stale-read detection
  updatedAt: string;    // ISO-8601; renderers mark stale past 5 min
  headline?: string;    // the one line the renderer leads with
  sections?: SurfaceSection[];
};

interface SurfaceRenderer {
  readonly id: string;  // matches SurfaceState.surface
  render(state: SurfaceState): string;  // host-agnostic payload (ANSI / HTML / widget lines)
}

interface SurfaceRegistry {
  register(renderer: SurfaceRenderer): void;
  render(id: string, state: SurfaceState): Result<string, SurfaceError>;
  has(id: string): boolean;
}

Result is the core error model type from 01-architecture. The built-in

watcher renderer is the one exception to the file rule: it synthesizes its

SurfaceState from status.json (attention items, phases, summaries), so

the hub agent is useful with zero extra writes — the default surface needs no

file because status.json already carries its state. Every custom surface

(pending and beyond) is file-backed.

Cadence

Decision. Event-driven with tight budgets: the watcher reacts to events,

never polls the filesystem, and its per-turn output is capped.

triggerwatcher actionbudget
agent_end (per session)re-summarize + attention scantrailing debounce 2 s per session (Clock); max 1 summary per turn, ≤2 sentences
tool result waiting on the userraise approval, phase waitingimmediate; 1 item per cause
assistant output question-shapedraise question, phase waitingimmediate; 1 item per cause
tool failureraise blocked, phase blockedimmediate
idle timeout (Clock)raise idle, phase idleonce per idle episode
answer observed (any path)resolve + resolution lineidempotent by attention id

Rules:

  • Max 1 summary per session turn, ≤2 sentences, action-oriented; appended to

summaries.jsonl as {t, sessionId, kind: "summary", text, by}.

  • The attention scan runs on waiting/failure tool results and on agent_end

— never on every event. Classification is one pass per event batch, not

per event.

  • Resolution is recorded once: the kind:"resolution" line is keyed by the

attention id; re-resolving the same id is a no-op (guarded in both the

watcher and the hub writer).

  • Debounce is per session, so a burst in one session collapses to one pass;

sessions stay independent.

  • While the watcher is down nothing is written and nothing is lost:

status.json and summaries.jsonl keep their last state, and the

restart catch-up pass covers the gap.

  • The watcher itself stays cheap: model via OMP_HUB_MODEL (small and fast

beats frontier here), restart on-failure with bounded backoff, and no

polling loops — the Clock port provides the only timers (idle timeout,

summary debounce).
